## 2. 第一次方向收敛：claim 覆盖式聚合

读完交接文档与 survey 后，判断 SALR 的落地方式有三个硬伤：

1. 成本：逐篇 LLM 抽命题 ≈ 6000 次调用/600 题，把一个检索层问题做成 LLM 流水线。
2. 基线选错：最强基线不是 BM25，而是 HyDE（同一动机、极便宜）。
3. distractor 10 篇候选会让收益虚高。

于是提出重构：**把 gap 从"LLM 打分的副产品"改成"聚合方式"问题**。

- 表示：query → 3–5 条原子 claim（一次 LLM 调用）。
- 打分：`Σ_c w_c · max_span sim(c, span)`，覆盖式聚合而非整句 max。
- 闭环：未覆盖 claim 直接渲染下一跳。

给用户两个选择（核心设计 / 语料），用户选 **C：A 线为主线，B 线（LLM 槽位判定）作为 oracle 上界**；语料选 **A：HotpotQA distractor 20 题**。

## 3. Pilot（20 题）：实现与第一次结论

新建 `src/`：

```
llm.py        双端点轮询 + sqlite 缓存 + 强制关思考 + JSON 剥离/修复
data.py       HotpotQA distractor → 每题 10 段候选，金标= supporting_facts
retriever.py  文档级 + 句级 BM25（k1=1.5, b=0.75）
claims.py     query → 原子 claim
coverage.py   max / mean / min / 阈值覆盖 / hybrid
slotjudge.py  B 线：逐 (query, passage) 槽位覆盖判定
eval.py       MRR / nDCG / Recall / AUC / bootstrap / 配对 bootstrap
run_pilot.py  分阶段、增量写盘、断点续跑
```

### 3.1 三个实现 bug

**Bug 1：`str.format` 吃掉花括号。**
`CLAIM_PROMPT` 里有 `answer_type in {person, date, ...}`，`prompt.format(question=...)` 直接 `KeyError`。
修复：改用 `.replace("{question}", question)`。

**Bug 2：claim 过滤条件过严。**
最初要求每条 claim 都必须含 `?`，结果把合法的中间跳（如 `Thomas Fitch defended John Henry Holliday in the case of...`）全部丢掉，只剩一条 `$c1 occurred on ?`，看起来像自引用。
修复：中间跳是**可核验的完整事实**，不该被过滤；只要求最后一条含 `?`。为此引入 `_bad_plan()`：空计划、无占位符、`$cX` 引用位置不合法才重试。

**Bug 3：引用位置校验用了模型的 id 而不是列表位置。**
模型会输出 `id=c2` 作为第一条 claim，导致自引用检查失效。
修复：按列表位置判断 `$cX` 是否 `X >= 当前位置`。

### 3.2 结果（20 题）

| 方法 | MRR@10 | AUC(answer) |
|---|---|---|
| BM25 整句 | 0.790 | 0.609 |
| claim_max | 0.754 | **0.707** |
| claim_mean | 0.668 | 0.648 |
| claim_min | 0.467 | 0.457 |
| claim_cover | 0.548 | 0.619 |
| hybrid_0.3 | **0.846** | 0.621 |
| judge_tb（B 线上界） | **0.957** | 0.653 |

结论（当时）：

1. 对齐信号存在（oracle MRR +0.167），但便宜近似只回收约 1/3。
2. 覆盖必须是软的：`min` 比 BM25 低 0.323。
3. 覆盖信号应叠加而非替换。

### 3.3 自己抓到的错误：平局伪影

用户问"LLM 判定是什么、为什么要蒸馏"，回去查原始记录时发现：

- 200 次判定里只有 39 个 `covered=true`，**2/20 题全 0**。
- 第一版用"文档原始顺序"破平，把这类题的排序当成了判定器的功劳。
- `Duffy Jackson` 和 `Biathlon` 两个"案例"都是伪影。

修复：新增 `judge_tb`，用 BM25 破平；MRR 0.938 → 0.957，Δ+0.167 [+0.058, +0.283]。同时改写 `PILOT.md` 的案例与已知问题。

**教训：oracle 类指标必须显式定义平局规则。**

## 5. E0：两个受控探针

### 5.1 E0-a 语义等价改写

设计：把金标段落按四类失配（关系同义、实体别名、语序倒装、事实分散）改写，做双向等价校验，只保留等价对；同一池内比较改写体相对原始体的排名变化。

实现：`src/probe.py`。80 条改写，64 条通过等价校验。

| 风格 | BM25 整句 | claim_max |
|---|---|---|
| relation 同义 | +2.25 | +4.12 |
| alias 别名 | +3.18 | +6.09 |
| inversion 倒装 | +0.05 | +2.00 |
| dispersal 分散 | +0.88 | +0.82 |

**负结果，但有用**：claim 级匹配掉得比整句 BM25 更狠，因为两者都是词面匹配——只换了"比什么"，没换"怎么比"。

### 5.2 E0-b 冗余盲

设计：池子 = 2 金标 + 它们的等价改写（同样覆盖对应需求）+ 6 负例；覆盖标签用 oracle，排除匹配器噪声。

实现：`src/e0.py`。

| k | 逐点 top-k | 覆盖式选择 |
|---|---|---|
| 1 | 0.250 | 0.500 |
| 2 | 0.500 | **1.000** |
| 4 | 0.650 | 1.000 |
| 6 | 0.750 | 1.000 |

+0.5 的差距，但池中近重复是**构造出来的**，只能当上界。此结论在 E1 被证伪（见下）。

## 6. E1：自然语料上的损失分解

数据源：MuSiQue validation 200 题（每题 19–20 段），`question_decomposition` 提供逐跳金标。

实现：`src/musique.py`、`src/e1.py`。

### 6.1 每题自带池

| k | 逐点 | 覆盖式 | 逐点冗余率 |
|---|---|---|---|
| 1 | 0.167 | 0.400 | 0.000 |
| 2 | 0.306 | 0.799 | 0.000 |
| 3 | 0.378 | 0.951 | 0.000 |
| 4 | 0.433 | 1.000 | 0.000 |

**逐点冗余率 0.000**：自然语料里没有"选两篇同义段落"这回事。E0-b 的机制被证伪，真实损失是"预算花在不覆盖需求的干扰项上"。

### 6.2 大池

3999 段，候选 = BM25 top-50：

- 候选 recall@50 = **0.610**（任何选择器的天花板）
- 覆盖式选择 k=3 打到 0.610
- 逐点 k=3 只有 0.288（用满天花的 47%）
- top-k 同题重复率：k=2 0.315、k=4 0.580

**损失分解**：`coverage = 候选召回 × 选择效率 = 0.610 × 0.47 = 0.29`。

写进 `RESEARCH_PLAN.md` 的核心图。

## 7. E2a：天花板是不是 BM25 特有的

实现：`src/e1_dense.py`、`src/e2a_hyde.py`。用 transformers 直接做 mean-pooling（未装 sentence-transformers）。

| retriever | 候选 recall@50 | 逐点 k=3 |
|---|---|---|
| BM25 | 0.610 | 0.288 |
| MiniLM | 0.760 | 0.424 |
| BGE-small | 0.765 | 0.431 |
| HyDE + MiniLM | 0.770 | 0.417 |

**换更强编码器、加 HyDE，天花板都钉在 0.77 附近。**

额外观察：HyDE 相对 BM25 +0.16，但相对**同编码器的 dense** 只有 +0.01——它的增益主要来自"词面换稠密"，不是假设文档本身。

## 8. E2b：要不要训模型（第一次判决）

用户提供了一个 GPU 上的 CE 服务（`10.52.100.210:8833`）。接口与预设不同：

- `/rerank` 字段是 `documents`，返回 `results[{index, score, document}]`，按分数降序
- 分数是**原始 logits**（9.20 / -11.33），不是概率
- `/score` 按 pairs 顺序返回；`/embed` 384 维已归一化
- `/health` 显示 `device: cuda`

写 `src/ce_client.py`：按 index 还原顺序，阈值前过 sigmoid，内网 `proxies={}`。

### 8.1 两个自己制造的坑

**坑 1：覆盖选择用了金标标签算增益。**
第一版 `greedy(scores, covers, k)` 里 `covers` 是金标，结果"CE 覆盖"与 oracle 完全重合——等于作弊。
修复：用 `sigmoid(CE)` 估计覆盖，阈值 τ ∈ {0.3,0.5,0.7}，评估始终用金标。

**坑 2：本地 CPU 训练/推理太慢。**
200 题 × 50 候选 × 约 4 跳 ≈ 7.6 万对，CPU 预计 10+ 小时。
修复：接远程 GPU 服务，200 题 2 分 19 秒。

### 8.2 结果（200 题）

| k | dense 逐点 | CE 逐点 rerank | CE 覆盖 τ=0.3 | oracle 覆盖 |
|---|---|---|---|---|
| 2 | 0.365 | 0.415 | 0.599 | 0.693 |
| 3 | 0.424 | 0.459 | **0.677** | 0.756 |
| 6 | 0.516 | 0.570 | 0.711 | 0.760 |

**判决**：CE 逐点 rerank 只有 +0.035；CE 覆盖 +0.253，拿到 oracle 的 90%。→ **不训练专用 grounding 编码器**，C2 降级为"覆盖选择器"。

（这个结论后来在 E6 被部分修正：粗粒度覆盖选择不需要训练，高难度 gap case 需要。）

## 9. E2c：绑定是因果原因

按跳位置拆开召回，发现崩塌：

|---|---|---|
| 0 | 0.915 | 0.795 |

| 2 | 0.673 | 0.554 |
| 3 | 0.538 | 0.256 |

| 跳位置 | dense | BM25 |

| 0 | 0.970 | 0.945 |
| 1 | 0.935 | 0.940 |
| 2 | 0.921 | 0.891 |

## 10. E3：自动绑定与误差传播

实现：`src/e3_binding.py`。计划用金标（隔离规划误差），四种条件：`none` / `decomp` / `oracle` / `pred`。

### 10.1 三次修 bug

**Bug 1：把池内位置当成了检索排名。**
`rank = keys.index(gkey) + 1` 给的是池中下标，导致所有模式的 recall 完全相同。
修复：`rank = sum(1 for s in scores if s > scores[gi]) + 1`。

**Bug 2：端到端只算了 `pred`。**
`e2e` 字典固定只取 pred，缺基线对比。
修复：四种模式各存末跳答案与 EM/F1。

**Bug 3：第 0 跳的增益被误归因给绑定。**
`none` 用整句问题，而 oracle/pred 第 0 跳已用分解后的跳查询——第 0 跳的差异是分解，不是绑定。
修复：新增 `decomp` 模式（跳查询、不绑定），把两者拆开。

### 10.2 结果（200 题）

端到端 EM：

| 模式 | EM | F1 |
|---|---|---|
| none | 0.050 | 0.134 |
| decomp | 0.105 | 0.172 |
| oracle | 0.365 | 0.489 |
| pred | **0.195** | 0.267 |

配对 bootstrap：`decomp−none` +0.055 [+0.020,+0.090]；`pred−decomp` +0.090 [+0.045,+0.140]；`oracle−decomp` +0.260 [+0.200,+0.320]；`pred−oracle` −0.170 [−0.225,−0.110]。

**误差传播吃掉约 65% 的绑定收益。**

## 12. 用户质疑方向偏离 → 回到语义 gap

用户问："我要求的优化点是什么？这个和我要求的任务方向有关系吗？"

复核后承认：

- 对题的：E0-a（等价改写）、E0-b/E1（覆盖目标）、E2b（语义匹配）。
- 偏掉的：E2c/E3/E4 的主线是**绑定**，属于多跳结构问题，不是语言学意义的语义 gap；E4 的主指标还是 EM，正是 survey 指出的"用下游指标间接反映"。

关键数字：E3 oracle 绑定下 recall@50 = 0.94，**纯语义 gap 导致的召回失败最多 6%**。这解释了为什么 gap 在主线上"消失"——是语料/粒度让 gap 没有生存空间。

遂决定：换 chunk 级粒度，直接测量 gap。

## 13. E5：语义 gap 的直接测量

### 13.1 第一次测量是伪影

初版用句级切分 + "chunk 含答案"定义 gold。抽查发现：

- `John Cabot (Italian: Giovanni Caboto; c. 1450 -- c.` —— 分句器在 `c.` 处切断
- `Which region has the 2nd largest rain-forest` —— top-1 才是正确证据，gold 标签错了

修复：改用**固定 40-token 滑窗、stride 20**，gold = 含答案 token 序列的窗口；答案匹配加词边界。

### 13.2 测量（200 题、14,289 chunk、540 跳）

| 检索器 | R@1 | R@3 | R@50 | gap 占比 |
|---|---|---|---|---|
| BM25 | 0.495 | 0.644 | 0.879 | 23.6% |
| Dense | 0.618 | 0.735 | 0.911 | **17.6%** |

### 13.3 消除（95 个 gap case）

| 手段 | 消掉 | 消除率 |
|---|---|---|
| 查询改写（3 条 paraphrase，max 合并） | 9 | 9.5% |
| 查询投影成陈述句 | 30 | 31.6% |
| **CE 语义重排** | **34** | **35.8%** |
| CE + 父段落上下文 | 34 | 35.8% |

整体 R@3：0.735 → 0.798（+6.3 点）。

**结论**：gap 不是"查询措辞不像文档"；查询侧改写基本无效，唯一有效的杠杆是匹配器能力。

实现坑：embedding 缓存文件名没带语料规模，200 题时误用了 100 题的 embedding（IndexError）。修复：文件名带 `len(corpus)`。

## 14. E6：可消除的上限

对 95 个 gap case 的 dense top-20（64 个 case 的 gold 在候选内）用 LLM 逐对打分（0–10）。

| 打分器 | 全部 95 | 可达 64 |
|---|---|---|
| CE | 37.9% | 56.2% [43.8,68.8] |
| LLM | 49.5% | **73.4%** [62.5,84.4] |
| 差值 | +11.6 [+5.3,+18.9] | +17.2 |

$$\text{gap closure} = 0.674 \times 0.734 = 0.495$$

**判决**：33% 的 gap case 在 top-20 里没有 gold（rerank 无解）；可达部分有 17 点可学。
→ 训练重新成立，但只针对高难度 gap case（修正 E2b 的结论）。

## 15. E7：蒸馏与交接

- 收集 5400 条 `(hop query, chunk, LLM 分数)`，覆盖 540 跳的 dense top-10。
- 按问题 id 分组切分（70/30），避免同一问题的 chunk 跨集泄漏。
- 训练 ms-marco-MiniLM-L-6-v2，3 epochs，lr 2e-5，batch 64，max_len 128。
- 本地 CPU：实测 19.4 s/步（`padding='max_length'` 浪费 3 倍），2 epochs 约 77 分钟。
- 改为 GPU 交接：T4 约 1–3 分钟，A10/3090 < 1 分钟。
- 打包 `dist/e7/`，起 HTTP 服务 8869 提供下载。

结果待回传（失败线：可达子集 closure@3 < 0.62）。

# 续篇（2026-11-04 夜 – 11-05）：难例挖掘、蒸馏与定位调整

## 19. E8–E11：为什么"数据量"不是模型小的解药

### 19.1 E8：先扩到 400 题

用 dense top-50 挖四类样本（难正例 gold∈(3,50]，难负例排在 gold 前，易正例，易负例）：

| 类型 | 数量 | 教师判为充分 |
|---|---|---|
| 难正例 | 649 | 65.5% |
| 易正例 | 750 | 84.9% |
| 难负例 | 1,538 | **31.0%** |
| 易负例 | 1,080 | **32.6%** |

**发现一：gold 标签有噪声。** "含答案字符串"太严，约 30% 被标成负例的段落其实能支撑答案。

**发现二：按 gold 排名定义"难"不可靠。** 改用**初始 CE 与教师的分歧**定义难度：一致率 69.8%，自信判错 892 条。

### 19.2 E7 的真正病因

E7 的 5,400 对里：

- 难正例（gold 在 top-3 外）只有 **50 条（0.9%）**；
- 学生给易正例平均分 **+4.00**，给难正例 **+0.83**，给负例 **−4.86**；
- 训练 AUC 0.989、测试 AUC 0.962 → **不是容量问题，是难例太少**。

结论：模型不小，数据总量也不是关键；**难例占比**才是。

### 19.3 E9 / E10：扩大挖掘

| 版本 | 题目 | 总对数 | 难正例 | 难负例 | 自信判错 |
|---|---|---|---|---|---|
| E9 | 1,000 | 16,643 | 1,772 | 7,449 | 3,698 |
| E10 | 2,417 | **36,929** | **4,263** | **18,242** | **8,411** |

E10 达到用户要求的"万级难例"（22,505 条）。

### 19.4 两套评测口径差一个数量级

训练包内报告：gap 档 **0.817 → 0.916**（每跳约 10 个候选）。
本项目真实口径（dense top-20、175,642 chunk、726 留出题、582 个可达 gap case）：

| 打分器 | closure@3 | closure@10 |
|---|---|---|
| dense | 0.000* | 0.601 |
| BM25 | 0.081 | 0.491 |
| base CE | 0.198 | **0.759** |
| **E10 蒸馏** | **0.227** | 0.749 |
| LLM 判定 | 0.170 | 0.737 |

\* gap 定义即 dense 在前 3 外。

蒸馏 **+2.9 点**（CI [+0.7,+5.0]），远低于精选候选上的 +9.8。

### 19.5 关键负结果：LLM 不是上界

E6 在小样本（64 个可达 case）上得到 LLM 73.4%，当时据此认为"有 17 点可学"。
扩到 582 个 case 后，**LLM 的 top-3 只有 0.170，低于 base CE 的 0.198**。

原因：绝对"是否充分"判定大量给 0，平局一多就退回 dense 顺序；成对判定中 **47.9% 被判平局**（E11）。

**教训：小样本的 oracle/上界数字不可信，必须扩到几百例再下结论。**

8,546 对（gap 跳 ×3 负例、易跳 ×2 负例），A/B 随机换位；4,096 判平局，4,450 可用；非平局中 89.3% 选 gold。

## 20. 定位调整：从"gap 消除"到"binding, not matching"

早期文档写的是"语义 gap 消除方法"。随着证据积累，这个说法站不住：

1. 查询改写只消 9.5% 的 gap（E5）——gap 不是措辞问题；
2. 匹配器蒸馏在真实口径只 +2.9 点（E10）——不是匹配器问题；
3. 绑定让按跳召回从 0.54 回到 0.92（E2c）——**是绑定问题**。

因此三份文档统一改写为：

> RAG 的 query–证据 gap，主要不是"不够像"，而是**需求变量没有绑定**；绑定后第一段崩塌消失，剩余损失 = 可达性 × 匹配能力。

贡献相应改为：

- **C1 诊断**：gap = 未绑定 + 选择错位，给出直接度量；
- **C2 方法**：plan-conditioned grounding（计划 → 绑定 → 逐需求 CE → 覆盖选择 → 可验证停止）；
- **C3 负结果**：查询改写无效；LLM 绝对充分性判定不是上界。

不再承诺"消除 gap"，改为"诊断 + 方法 + 负结果"。
